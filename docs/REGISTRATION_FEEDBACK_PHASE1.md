# 報名第一階段：進度與結果確認

## 行為

本人與家庭選手共用的 `joinTournamentAsPlayer` 現在會從預查開始顯示進度。同帳號同場的同頁重複操作共用同一個 in-flight Promise，不因重繪或改由另一入口點擊而再送一筆。

真正送出前，保留本次選擇的選手識別碼；家庭報名另保留白名單限定的原請求內容及 operationId，不保存姓名、電話、電子郵件或完整玩家資料。此紀錄只供恢復進度，不是報名成功的證據。儲存功能被瀏覽器阻擋時仍允許原流程報名，但提示使用者留在此頁確認結果。

8 秒仍未結束時，透過既有 `familyRegistration({action:'mine',code})` 讀取登入帳號的報名狀態。必須本次選擇的每個識別碼都在有效狀態，才可確認目前報名狀態；不能用家長或另一名孩子的紀錄代替。查詢為空、逾時、失敗或已取消都不能直接宣稱報名失敗。

自動查詢有次數上限、讀取逾時與退避，避免所有等待者密集輪詢。手動查詢合併執行中請求並限頻。65 秒沒有明確結果時，外層操作會回覆「結果尚未確認」，保留狀態與查詢入口。未真正送出的預查若逾時，晚到的預查回覆不得再觸發寫入。

重新整理後只自動讀取，不自動重送。個人／家庭報名在原請求內容完整時，提供明確的「重送原報名」按鈕，沿用同一個 operationId、選手、正備取配置與資格確認；由既有後端 idempotency 判定重播或執行，不另建新請求。原配置改變仍依原有後端規則拒絕，不會靜默接受備取或改動排序。

登入帳號改變時清除記憶體顯示與查詢計時器，保留各帳號自己的待確認紀錄供下次登入查詢。介面只顯示房號、進度與正／備取狀態；恢復確認後通知既有大廳或詳情頁重新讀取報名資料。

## 範圍

不修改後端函式、Security Rules、名額容量、正備取排序與分配交易。不宣稱解決尖峰交易競爭。抽籤型個人報名經共用入口可顯示進度與讀回 pending_draw，但其獨立服務沒有持久化的原操作編號，因此不提供原請求重送。團體賽專用的 submit-team-registration 流程維持既有行為；本階段針對這次個人賽搶報入口。

此處防連點作用於同頁同帳號同房間，並能從已保存的待確認紀錄恢復；不宣稱跨分頁同時點擊具備全域互斥鎖。後端仍負責選手唯一性與名額一致性。
