# 送分穩定性整合候選與實戰驗收

本候選整合 #802 送分階段診斷、#803 分桶已提交回覆及 #804 雙房四台加兩台測試。目的為準備下一次受控實戰；候選完成不代表已部署或正式房間已啟用。

## 本次行為

- 舊版後端記錄請求各階段耗時與交易 callback 次數，完成紀錄只在交易成功返回後產生，不記錄玩家姓名、UID 或比分快照。
- 既有分桶仍為四台一桶。逐筆加分、失誤、撤回、重賽、暫停與恢復只更新相關桶、操作收據及稽核；不以公開對戰表更新作為這些操作的完成條件。
- 前端核對已提交回覆中的桶身分、epoch、比分版本及結構後更新權威比分；無效回覆仍走原有訂閱核對，保留原操作編號防重複。
- 確認勝負、跨桶晉級、調度與裁判席仍有結構性一致性要求，本次沒有把所有操作改成獨立交易。
- 每台一桶、每場一文件、報到與抽籤重構不在本次範圍。同桶仍可能競爭；不能以本候選宣告容量問題已解決。

## 持續送分測試

`tests/four-court-buckets/continuous-scoring-emulator.cjs` 在隔離 Firestore Emulator 建立四台及兩台的兩間房。六台各自連續加分、撤回，僅等待本台的正式回覆，不等待其他台或公開顯示。預設每台六輪，共 72 筆操作，另重送六筆已完成操作以核對去重。

測試期間關閉自動公開更新，驗證權威比分仍可提交，且房間根文件及公開文件均未被逐筆計分修改；最後用內部投影器追上所有桶版本。檢查比分、每場版本、收據及稽核筆數，並記錄每筆延遲與 Firestore 交易 callback 次數。這與 #804 的應用層重送計數不同。

延長測試可設定 `BXH_SCORE_LAB_CYCLES` 為 1–120。結果輸出至 `test-results/four-court-buckets/continuous-scoring.json`。交替加分與撤回是合成負載，未模擬完整賽程、正式網路、Cloud Run 冷啟動、原生 Callable 與 App Check，也不能據此推算實戰延遲。

## 發布前必須完成

1. 核對現行正式前端版本、Functions 來源與 revision、Rules release 和房間開關；保留線上的社群裁判、合作主辦及計分引擎修復。不可把儲存庫 functions 目錄直接整包部署。
2. 在同一整合提交通過裁判邏輯、分桶權限、原生 Callable、完整頁面及自動公開更新 CI。實機再驗證原生 Auth/App Check。
3. 先在新建的專用驗收房確認讀寫、主備交接、撤回、防重複、重連、晉級與結果恢復。保留 BXH-XAYH7W 的既有賽事進度，未核對前不對它切換。
4. 指定下一次驗收房號後，只開放該房與 epoch。功能環境、讀取 Rules、後端、前端及轉換必須配套；同一房不得新舊 writer 並行。
5. 驗收期間同時記錄權威提交成功率與延遲、交易重試、未知結果、公開同步落後，以及實際服務 revision。診斷尚未覆蓋所有桶分後端階段，不可將舊版診斷直接視為桶分全鏈路量測。

## 下一次實戰與停止條件

採用實際安排的房間與台數；重現 2026 年 11 月 14 日配置時為四台加兩台。測試送分、失誤、撤回、同時完賽、換裁判及斷線重連；每段對照權威比分、公開版本及晉級。

- 比分、版本、稽核或晉級不一致：立即停止新增操作並核對，不以重按加分解決。
- 回覆逾時而結果未知：保留同一操作編號，先核對收據；不得當成未寫入而另建一筆加分。
- 公開畫面落後但權威收據正確：單獨追查投影與觀戰，避免誤判送分失敗。
- 持續出現長延遲：停止擴大試點，依交易重試及各階段證據評估同桶競爭、服務容量或同步等待。

## 回復

暫停送分後，先保存目前 epoch、桶版本與收據，將最新權威桶結果合成完整狀態並核對公開對戰表、比分與晉級，再執行既有受控回復程序。不可直接移除 scoreStorage、切回舊 writer 或拿切換前的根文件覆蓋新比分。回復完成且裝置重連驗證後才恢復送分。

本文件沒有指定未經確認的正式房間，也沒有自動切換正式開關。
