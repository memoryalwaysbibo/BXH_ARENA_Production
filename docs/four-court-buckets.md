# Four-court scoring buckets: isolated candidate

The current score and confirmation transactions update both `tournaments/{code}.data` and `publicTournaments/{code}.bracketView`. The three-seat callable does too. Therefore a court-to-bucket label alone cannot reduce contention: all operations would still write the two shared room documents. The 2026-10-31 incident cause remains unproven. See the baseline in PR #679.

This PR contains a **non-runtime** routing and Firestore Emulator candidate. It does not alter the app entrypoint, production Rules, Functions, flags, rooms or deployed scoring. It creates no production collections. An emulator pass is evidence for partition behavior, not certification of a six- or twelve-court live event.

## Mapping

For positive court number `s`, bucket index is `floor((s - 1) / 4)`. ID `court-1` stores courts 1–4, `court-2` stores 5–8, `court-3` stores 9–12, and so on. The count is `ceil(stations / 4)`; the organizer does not configure a bucket count. Normal Firestore document size, write rate, transaction and billing limits still apply; “automatic” does not mean physically unlimited capacity.

The candidate stores only its own court matches and receipt documents under `tournaments/{code}/scoreBuckets/{bucketId}`. A synthetic score transaction writes one bucket and its idempotency receipt. The room and public mirror remain unchanged during that transaction. A projection reader verifies all bucket identities and match routes before combining their scores with the structural room state. The unit tests cover boundaries 4→5 and 8→9, scope, stale revisions and incomplete projections.

The emulator suite launches six and twelve requests together for two repetitions, comparing a synthetic shared-room-document control with the bucket candidate. It records successes, failures, callback attempts and elapsed times. The control is **not** the full existing app transaction. Admin SDK transactions use server-side locks, so callback retry counts are not directly comparable to the browser SDK result in PR #679. An emulator result cannot establish production throughput or explain the incident. Receipt and score checks ensure acknowledged writes persist once, and the candidate must not change room/public document update times. These are synthetic non-scoring room codes in the `demo-bxh-four-court-buckets` project; the test refuses any other host/project before constructing Firebase clients. Rules deny all client access and are lab-only.

## Required before a production rollout

1. Make a versioned server-owned room cutover: prevent every old client and callable from writing `data` or `bracketView` after score buckets become authoritative. Seed and verify buckets from a frozen canonical state; never let an old whole-room retry overwrite a newer bucket score. Fail closed on missing, mismatched or partial bucket sets.
2. Move all normal score, undo, fault and three-seat commands to the bucket authority with the current seat, identity, dispatch and revision checks. Maintain operation receipts so lost replies cannot double-score. Pure score writes must not touch the room or public mirror.
3. Handle confirmation, winner propagation, same-round changes, venue transfers, retirement and bracket edits as structural operations. Lock or validate affected bucket revisions, including cross-bucket successor matches. Keep accepted results and ledger/audit data atomic. Full-rules, other tournament formats and settlement must be covered before release.
4. Materialize a public projection from bucket revisions using a single controlled writer or another bounded fan-in, and let private referee pages read the authoritative bucket for their court. Reject late projections with older revisions. A public view can lag briefly, but must converge without mixing old room scores into new results.
5. Define migration and rollback separately. A feature flag starts disabled. Disabling after cutover is unsafe until a server process has rebuilt and verified the old room snapshot from every bucket; rollback cannot rely on the stale root `data`. Test interrupted migration, stale clients, network loss and mixed-version users. Complete 6/12-court emulator and isolated UI tests, then a supervised live test room.

The candidate deliberately has no rollout flag or wiring. Its synthetic `compose` overlays only scores and revisions; the separate trusted adapter below handles its scoped confirmation cases. Neither certifies public subscriptions or settlement.

## Trusted scoring adapter candidate

`referee-seats/functions/bucket-scoring-service.cjs` adds a second, production-shaped experiment using the existing three-seat authorization and scoring engine. Its constructor requires the exact local Emulator project and host, and it is not exported as a Firebase callable. A synthetic release configuration and room generation are still required before the handler runs. It cannot activate production scoring.

The existing `transition` API keeps its normal full progression behavior. A separate `transitionLocal` permits only score, fault, undo, rematch, pause and resume, preserving seat/player/dispatch/score checks and canonical round events while deferring global progression. Local transactions read the room authority and one full-match bucket; they write that bucket, unique receipt and audit only. They return a bucket patch, not a falsely current full-room snapshot.

Confirmation and quick decisions read every bucket in one transaction, run the existing complete progression engine, then atomically update affected buckets, the structural room snapshot, public projection, receipt, audit and staff duty record. This deliberately retains room-wide contention at confirmation; the candidate only removes it from ordinary scoring. A complete root snapshot written on confirmation is valid at that transaction's commit, and later local scores are authoritative in buckets. Missing buckets, mixed generations, stale participant routing and old score revisions stop the operation.

`bucket-public-projection.cjs` adds an emulator-only internal projection worker. It reads the structural room and every authoritative bucket in one transaction, then writes only the public projection. A generation plus per-bucket revision vector deduplicates identical publication attempts; late retries reread current bucket versions before publishing. Court status follows the current match in the bucket, so pause/resume does not show a stale court status. Scoring does not call this worker or synchronously write the public document. A production event trigger and bounded publication cadence are still required.

`trusted-emulator.cjs` covers concurrent trusted 6/12-court scoring with unchanged root/public update times, public projection after score and pause/resume with concurrent-worker deduplication, two courts in different buckets confirming the same successor, final placement, a lost-reply replay, conflicting operation reuse, stale score revisions, unauthorized/revoked seats and generation/release mismatch. The test room state and identities are synthetic. Migration, public subscription/worker scheduling, non-three-seat writes, partners, dispatch commands and rollout/rollback remain required before release.

## Legacy write fence candidate

The existing three-seat callable uses Admin SDK and bypasses Firestore Rules. Its scoring handler now rejects any room with a `scoreStorage` field, regardless of manifest status or command, before parsing or changing score state. The production-shaped candidate Rules file also rejects every browser create/update/delete that would introduce, edit or delete a bucket room; it rejects browser writes to that room's public mirror and all bucket writes and all receipt reads/writes; the opt-in staff bucket read path described below is separate. The manifest can only be installed or removed by a separately verified server migration. Unmarked rooms keep the existing rule branches and scoring handler behavior.

This is a **fail-closed cutover guard**, not an activation path. Once the marker exists, legacy metadata, registration counters and other browser room edits will also fail. Do not mark a live room until those paths, the new private score view, public worker and migration are fully connected. Other Admin SDK services that write whole-room scores still need their own guards. The Rules in this PR are a candidate file, not deployed production Rules; CI tests them with a simulated admin account against the Emulator.

## Atomic cutover and rollback experiment

`bucket-cutover.cjs` is an internal Emulator-only factory, with no callable or deployment hook. Activation requires the caller's exact room update time, an enabled lab configuration, an unmarked canonical room and public mirror, and an empty bucket set. A single transaction creates every four-court bucket, adds the room generation marker and initializes the public generation vector. If the room changed or an orphan bucket exists, it writes nothing. The room's existing `data` remains a structural snapshot after activation.

Rollback requires the exact generation. One transaction reads the room and all buckets, validates identities and structural consistency, reconstructs full score ledgers, updates the room and public bracket, removes the generation marker and projection vector, and deletes the bucket documents. A conflicting score transaction must retry against the new state or fail. Unit and Emulator tests cover 6/12-court round trips, stale root scores, wrong generation and an interrupted/partial seed. Historical score operation receipts and audit records remain for investigation and are not replayed into the room.

This only demonstrates an atomic data boundary in a demo project. Other Admin SDK writers still bypass Rules; the private UI and production public worker are not connected. A real cutover additionally needs an inventory and fence for those writers, controls for concurrent room operations, schema/size checks for each tournament format, and a supervised production rollout. Do not invoke this experiment on a live room.

## Server writer inventory

The repository search found multiple trusted services which serialize `tournaments/{code}.data` and sometimes `publicTournaments/{code}.bracketView`. The current candidate blocks the old three-seat scorer, seat ownership callable and promotion callable when a room has a `scoreStorage` marker. These checks precede receipts/replays and writes. An Emulator case checks all three calls reject without changing the room or public mirror. For an active bucket room, preventing seat changes is an intentional temporary safety lock; a bucket-aware seat operation is required before rollout.

QR check-in, roster mutations, room-access configuration, onsite draw transactions and hosting completion cleanup now reject or skip bucket-marked roots before serializing room state. The pinned legacy writer transaction wrapper also rejects marked roots that it has read. Emulator tests cover the QR, roster, room-access, onsite and wrapper entrypoints with unchanged room/public update times and no operation receipts. Hosting cleanup is a trigger and still needs a dedicated end-to-end test. The wrapper only checks roots visible in its transaction; other Admin SDK writers outside this inventory may remain. These guards deliberately disable those old operations for bucket rooms; bucket-aware replacements are required before rollout. Browser `cloud-runtime.js` direct writes need the bucket-aware UI/subscription route. Read-only summary and staff-roster services do not serialize the room bracket in this inventory. This list is a route inventory, not a claim that every Admin SDK writer is fenced.

## Bucket-aware seat candidate

`bucket-seat-service.cjs` is an Emulator-only replacement experiment for claim, leave, revoke, request, respond and cancel. It reuses the existing seat transition and authority checks, rejects partner rooms, and requires both the seat and bucket release configurations. It reads root, all buckets and then the public mirror in the same transaction, reconstructs current scores, and applies seat metadata to that current snapshot. It does not update bucket documents. It updates public scores and display names together and records the bucket version vector; private seat UIDs, assignment arrays and requests are removed from public metadata.

Seat changes remain structural room transactions. Concurrent local scores either commit before the seat snapshot, or retry against the changed seat revision; acknowledged scores remain authoritative in buckets. Dedicated bucket seat receipts include the room epoch and reject conflicting operation reuse. The Emulator cases exercise backup claim, receipt replay, transfer request/accept, stale scoring, manager revocation, public field redaction, unchanged bucket update times and a seat-versus-score race. A fake production DB is rejected at construction.

This is not wired into the frontend or exported as a callable. The old seat handler remains fenced on marked rooms. The private subscription UI, rollout migration, public scheduling, partner events and the remaining room operations still need implementation and acceptance before production activation.

## Isolated referee browser client

`four-court-client.cjs` composes server-confirmed room and bucket subscription events into a private referee view. It waits for the complete bucket set, overlays the root seat authority, and rejects older root/bucket revisions, old listener callbacks and mixed epochs. Cache/pending events do not enable scoring. Offline or failed subscriptions disable commands. Commands contain typed intentions and current court/score/dispatch versions; they do not optimistically alter scores. An ambiguous reply retains the exact operation ID for an explicit retry, and a changed epoch blocks replaying that old intention.

`four-court-referee-lab.js` mounts a local-only panel using the existing `BXHRefereeSeats` controls. It accepts only a loopback page and the demo project transport. It provides station selection, simple score buttons, synchronization status and explicit reconnect/retry controls. It is not imported by the production entrypoint and does not replace the deployed score panel.

The browser test uses real Admin SDK Emulator listeners through a test-only bridge with a fixed synthetic identity. It exercises scoring, existing seat controls for claim/request/accept/revoke, scores retained across handover, blocked revoked seats, reconnect observing another bucket, and a reply deliberately lost after a successful score commit followed by idempotent retry. It captures mobile/desktop screenshots. This bridge is not a production subscription or callable; the separate Web SDK transport/Rules suite below verifies direct client reads. Real browser Auth integration and main-app lifecycle wiring remain required. Unit tests additionally cover late callbacks, cached events, listener failure, epoch change and old version rejection.

## Web SDK read transport and candidate authorization

`four-court-firestore-transport.cjs` accepts an already initialized Firestore/Auth instance and public Web SDK functions. It subscribes to explicit room/bucket documents, forwards cache/pending metadata, and pins the subscription and command identity to the current UID. A shared, server-confirmed own-profile subscription gates data delivery and commands. Deactivation, loss of staff role, sign-out or an account switch stops its listeners; cached profile data cannot grant access. A fresh Rules read is checked separately because an existing SDK target may briefly return an earlier server-confirmed snapshot after a profile change. It uses the server-owned numeric room `updatedAt` as the structural version because the Web SDK does not expose Admin SDK document `updateTime`; candidate structural writers must keep advancing that value. It does not initialize Firebase, install a callable, or attach itself to the production app.

Candidate Rules permit only individual bucket GETs when `systemConfig/fourCourtScoreBuckets.privateReadsEnabled == true`, the room is an active supported official bucket room, the account is active non-test staff/admin, and the bucket identity matches its room/epoch/schema. The new read flag defaults to closed when absent. It is independent from the scoring release flag, allowing a separately controlled read view. Bucket list queries, every client bucket write and all receipt/audit access remain denied. Partner rooms are not supported yet. Staff read access matches the existing full private-room role policy: losing a court seat removes scoring authority while retaining staff viewing; deactivation removes private reading.

`reader-rules.cjs` uses the Firebase Web SDK and Rules test credentials, with the full candidate Rules installed in the demo Emulator. It verifies live 6/12-court composition and bucket updates, unseated staff/admin reads, denied player/anonymous/test/inactive reads, denied list/write attempts, account deactivation terminating a subscription, sign-out stopping transport access, and denied flag-off/wrong-epoch/partner/preparing-room reads. The Auth lifecycle object is injected in this test; it is not a production browser login acceptance test. Browser UI integration still uses its separate test bridge. The new read Rules and transport remain candidate code with no deployed configuration change.

## Browser Auth and existing command adapter candidate

`four-court-app-bridge.cjs` adapts a pinned bucket client to the existing `cloudSync` command/read interfaces. A successful score command waits for its authoritative subscribed score revision before returning a full state to the existing command function. Recovery reads use the composed view, never the stale root JSON. Unsupported dispatch commands and mismatched sessions fail closed. The adapter is explicitly constructed by the test page; it is not installed by the production entrypoint. Navigation/lifecycle installation for the full app remains required.

Authorization errors now stop room/bucket listeners and clear the client's private state. Network failures keep the last view read-only. The Auth fixture uses the real Firebase browser SDK and Email/password Auth Emulator login with synthetic accounts. It bundles the SDK locally, blocks non-loopback browser requests, and subscribes directly to Firestore under the candidate Rules; it does not use the previous Admin subscription bridge.

The fixture loads the exact `executeRefereeSeatCommand` source from the existing main app along with the existing seat controls. Its surrounding renderer/lifecycle is still an isolated harness. Score/seat commands use a local HTTP test adapter which verifies an Auth Emulator ID token and invokes the trusted candidate server core. It is not a deployed Firebase callable/App Check acceptance test. Cases cover 6/12 courts, scoring through the existing command function, account switching, clearing the old private view, account deactivation, rejected fresh login reads for a deactivated account, sign-out and player read denial. No production account or room is used.

## Callable and explicit frontend session candidate

`bucket-callable.cjs` defines two native onCall endpoints with App Check enforcement always enabled. Its wrapper requires verified Auth and App Check context before invoking the trusted core, preserves typed domain failures, and hides unexpected backend details. The definitions are not added to the production Functions index. The test builder creates a separate ephemeral Functions source package; every handler still requires the exact demo project and local Auth/Firestore hosts before constructing a trusted scoring service.

`four-court-session.cjs` builds the Web SDK transport, bucket client and existing command bridge using native `httpsCallable`. It defaults to disabled. Explicit start installs only a pinned session's cloud facade; stop restores the original facade only if a newer session has not replaced it. Network/timeout replies stay ambiguous so existing operation receipts can deduplicate retries. The actual app entrypoint still does not initialize this candidate session.

The browser suite additionally runs against Auth, Firestore and Functions Emulators with native SDK calls. It uses the same existing command function and verifies 6/12-court scoring, missing Auth/App Check rejection before writes, and a player's native Callable attempt being rejected even if request data claims a referee UID. The legacy local HTTP adapter is counted and must be unused in this mode.

App Check positive requests use an unsigned fixture token only on loopback in the demo project. Firebase's Functions Emulator enables its SDK debug verification path; this tests protocol/context enforcement and missing-token rejection, **not production attestation or token signature verification**. No debug verification setting is added to deployable code. Production App Check acceptance remains a release requirement. The pinned SDK behavior is visible in [firebase-functions v6.6.0 HTTPS provider](https://github.com/firebase/firebase-functions/blob/v6.6.0/src/common/providers/https.ts) and the [firebase-tools v14 Emulator environment](https://github.com/firebase/firebase-tools/blob/v14.0.0/src/emulator/functionsEmulator.ts).

## Automatic public projection trigger candidate

`bucket-projection-trigger.cjs` defines a v2 document-written trigger for match bucket documents. The function is bounded to one instance and one concurrent invocation, briefly gathers a burst, then calls the existing transactional projector with the event's epoch. The projector reads current root/buckets, never the event's scores. Duplicate version vectors are skipped; old epochs are skipped inside the transaction. Deleted/malformed events and removed/inactive rooms are skipped. Integrity or infrastructure failures remain failures for retry and investigation.

Automatic publication additionally requires `automaticPublicProjectionEnabled == true` in the existing score bucket configuration. Missing/false leaves it disabled. This guard is read in the publication transaction. The existing internal manual projector remains available for controlled catch-up; enabling the flag alone does not guarantee a new event, so activation needs an initial catch-up or a subsequent score event.

The trigger is exported only by the ephemeral Emulator source package. It is not added to the production Functions index. A real Firestore/Functions Emulator suite seeds complete 6/12-court rooms atomically, scores every court concurrently, and waits for public publication without manually invoking a successful projector. It checks preserved score logs, an unchanged private root, stale epoch/vector skips, a closed automatic flag and convergence after re-enable plus a new score. This proves the event path in the demo project, not production capacity or delivery latency.
