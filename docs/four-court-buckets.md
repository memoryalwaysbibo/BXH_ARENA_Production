# Four-court scoring buckets: isolated candidate

The current score and confirmation transactions update both `tournaments/{code}.data` and `publicTournaments/{code}.bracketView`. The three-seat callable does too. Therefore a court-to-bucket label alone cannot reduce contention: all operations would still write the two shared room documents. The 2026-10-31 incident cause remains unproven. See the baseline in PR #679.

This PR contains a routing and Firestore Emulator candidate plus closed-by-default formal Functions registration. It adds closed client lifecycle wiring to the app entrypoint, but does not alter deployed Rules/Functions, production flags, rooms or deployed scoring. It creates no production collections. An emulator pass is evidence for partition behavior, not certification of a six- or twelve-court live event.

## Mapping

For positive court number `s`, bucket index is `floor((s - 1) / 4)`. ID `court-1` stores courts 1–4, `court-2` stores 5–8, `court-3` stores 9–12, and so on. The count is `ceil(stations / 4)`; the organizer does not configure a bucket count. Normal Firestore document size, write rate, transaction and billing limits still apply; “automatic” does not mean physically unlimited capacity.

The candidate stores only its own court matches and receipt documents under `tournaments/{code}/scoreBuckets/{bucketId}`. A synthetic score transaction writes one bucket and its idempotency receipt. The room and public mirror remain unchanged during that transaction. A projection reader verifies all bucket identities and match routes before combining their scores with the structural room state. The unit tests cover boundaries 4→5 and 8→9, scope, stale revisions and incomplete projections.

The emulator suite launches six and twelve requests together for two repetitions, comparing a synthetic shared-room-document control with the bucket candidate. It records successes, failures, callback attempts and elapsed times. The control is **not** the full existing app transaction. Admin SDK transactions use server-side locks, so callback retry counts are not directly comparable to the browser SDK result in PR #679. An emulator result cannot establish production throughput or explain the incident. Receipt and score checks ensure acknowledged writes persist once, and the candidate must not change room/public document update times. These are synthetic non-scoring room codes in the `demo-bxh-four-court-buckets` project; the test refuses any other host/project before constructing Firebase clients. Rules deny all client access and are lab-only.

## Required before a production rollout

1. Make a versioned server-owned room cutover: prevent every old client and callable from writing `data` or `bracketView` after score buckets become authoritative. Seed and verify buckets from a frozen canonical state; never let an old whole-room retry overwrite a newer bucket score. Fail closed on missing, mismatched or partial bucket sets.
2. Move all normal score, undo, fault and three-seat commands to the bucket authority with the current seat, identity, dispatch and revision checks. Maintain operation receipts so lost replies cannot double-score. Pure score writes must not touch the room or public mirror.
3. Handle confirmation, winner propagation, same-round changes, venue transfers, retirement and bracket edits as structural operations. Lock or validate affected bucket revisions, including cross-bucket successor matches. Keep accepted results and ledger/audit data atomic. Full-rules, other tournament formats and settlement must be covered before release.
4. Materialize a public projection from bucket revisions using a single controlled writer or another bounded fan-in, and let private referee pages read the authoritative bucket for their court. Reject late projections with older revisions. A public view can lag briefly, but must converge without mixing old room scores into new results.
5. Define migration and rollback separately. A feature flag starts disabled. Disabling after cutover is unsafe until a server process has rebuilt and verified the old room snapshot from every bucket; rollback cannot rely on the stale root `data`. Test interrupted migration, stale clients, network loss and mixed-version users. Complete 6/12-court emulator and isolated UI tests, then a supervised live test room.

The frontend and migration deliberately remain unconnected; the formal server registration and its closed runtime gate are described at the end. Its synthetic `compose` overlays only scores and revisions; the separate trusted adapter below handles its scoped confirmation cases. Neither certifies public subscriptions or settlement.

## Trusted scoring adapter candidate

`referee-seats/functions/bucket-scoring-service.cjs` adds a second, production-shaped experiment using the existing three-seat authorization and scoring engine. Its default constructor requires the exact local Emulator project and host. The formal entry explicitly selects production mode with the additional deployment and per-room gates described below. A synthetic release configuration and room generation are still required before the handler runs. These candidate flags alone cannot activate production scoring.

The existing `transition` API keeps its normal full progression behavior. A separate `transitionLocal` permits only score, fault, undo, rematch, pause and resume, preserving seat/player/dispatch/score checks and canonical round events while deferring global progression. Local transactions read the room authority and one full-match bucket; they write that bucket, unique receipt and audit only. They return a bucket patch, not a falsely current full-room snapshot.

Confirmation and quick decisions read every bucket in one transaction, run the existing complete progression engine, then atomically update affected buckets, the structural room snapshot, public projection, receipt, audit and staff duty record. This deliberately retains room-wide contention at confirmation; the candidate only removes it from ordinary scoring. A complete root snapshot written on confirmation is valid at that transaction's commit, and later local scores are authoritative in buckets. Missing buckets, mixed generations, stale participant routing and old score revisions stop the operation.

`bucket-public-projection.cjs` adds an internal projection worker, defaulting to the exact local Emulator runtime. It reads the structural room and every authoritative bucket in one transaction, then writes only the public projection. A generation plus per-bucket revision vector deduplicates identical publication attempts; late retries reread current bucket versions before publishing. Court status follows the current match in the bucket, so pause/resume does not show a stale court status. Scoring does not call this worker or synchronously write the public document. The bounded trigger is registered behind the production runtime gate; deployment and real-site acceptance remain required.

`trusted-emulator.cjs` covers concurrent trusted 6/12-court scoring with unchanged root/public update times, public projection after score and pause/resume with concurrent-worker deduplication, two courts in different buckets confirming the same successor, final placement, a lost-reply replay, conflicting operation reuse, stale score revisions, unauthorized/revoked seats and generation/release mismatch. The test room state and identities are synthetic. Migration, public subscription/worker scheduling, non-three-seat writes, partners, dispatch commands and rollout/rollback remain required before release.

## Legacy write fence candidate

The existing three-seat callable uses Admin SDK and bypasses Firestore Rules. Its scoring handler now rejects any room with a `scoreStorage` field, regardless of manifest status or command, before parsing or changing score state. The production-shaped candidate Rules file also rejects every browser create/update/delete that would introduce, edit or delete a bucket room; it rejects browser writes to that room's public mirror and all bucket writes and all receipt reads/writes; the opt-in staff bucket read path described below is separate. The manifest can only be installed or removed by a separately verified server migration. Unmarked rooms keep the existing rule branches and scoring handler behavior.

This is a **fail-closed cutover guard**, not an activation path. Once the marker exists, legacy metadata, registration counters and other browser room edits will also fail. Do not mark a live room until those paths, the new private score view, public worker and migration are fully connected. Other Admin SDK services that write whole-room scores still need their own guards. The Rules in this PR are a candidate file, not deployed production Rules; CI tests them with a simulated admin account against the Emulator.

## Atomic cutover and rollback experiment

`bucket-cutover.cjs` is an internal Emulator-only factory, with no callable or deployment hook. Activation requires the caller's exact room update time, an enabled lab configuration, an unmarked canonical room and public mirror, and an empty bucket set. A single transaction creates every four-court bucket, adds the room generation marker and initializes the public generation vector. If the room changed or an orphan bucket exists, it writes nothing. The room's existing `data` remains a structural snapshot after activation.

Rollback requires the exact generation. One transaction reads the room and all buckets, validates identities and structural consistency, reconstructs full score ledgers, updates the room and public bracket, removes the generation marker and projection vector, and deletes the bucket documents. A conflicting score transaction must retry against the new state or fail. Unit and Emulator tests cover 6/12-court round trips, stale root scores, wrong generation and an interrupted/partial seed. Historical score operation receipts and audit records remain for investigation and are not replayed into the room.

This only demonstrates an atomic data boundary in a demo project. Other Admin SDK writers still bypass Rules; the private UI and production public worker are not connected. A real cutover additionally needs an inventory and fence for those writers, controls for concurrent room operations, schema/size checks for each tournament format, and a supervised production rollout. Do not invoke this experiment on a live room.

## Bucket-aware seat candidate

It reuses the existing seat transition and authority checks, rejects partner rooms, and requires both the seat and bucket release configurations. Seat changes remain structural room transactions. Concurrent local scores either commit before the seat snapshot, or retry against the changed seat revision; acknowledged scores remain authoritative in buckets. Dedicated bucket seat receipts include the room epoch and reject conflicting operation reuse. ## Automatic public projection trigger candidate

`bucket-projection-trigger.cjs` defines a v2 document-written trigger for match bucket documents. The function is bounded to one instance and one concurrent invocation, briefly gathers a burst, then calls the existing transactional projector with the event's epoch. The projector reads current root/buckets, never the event's scores. Duplicate version vectors are skipped; old epochs are skipped inside the transaction. Deleted/malformed events and removed/inactive rooms are skipped. Integrity or infrastructure failures remain failures for retry and investigation.

Automatic publication additionally requires `automaticPublicProjectionEnabled == true` in the existing score bucket configuration. Missing/false leaves it disabled. This guard is read in the publication transaction. The existing internal manual projector remains available for controlled catch-up; enabling the flag alone does not guarantee a new event, so activation needs an initial catch-up or a subsequent score event.

The trigger is registered by both the ephemeral Emulator package and the formal Functions index. The formal runtime remains disabled unless explicitly configured as described below. A real Firestore/Functions Emulator suite seeds complete 6/12-court rooms atomically, scores every court concurrently, and waits for public publication without manually invoking a successful projector. It checks preserved score logs, an unchanged private root, stale epoch/vector skips, a closed automatic flag and convergence after re-enable plus a new score. This proves the event path in the demo project, not production capacity or delivery latency.

## Explicit retry controls for uncertain outcomes

The formal referee recovery panel now shows a retry button while operations remain unresolved. It forwards only retained keys to the pinned client; no new score intention or operation ID is constructed. Score replay waits for the authoritative score revision, and seat replay waits for the authoritative seat model revision before reporting success. Unknown keys, wrong room/account, unsynchronized state and simultaneous retry attempts are rejected or suppressed.

For marked rooms the recovery action reconnects the existing client instead of backing up and reloading the page. Network-failed recovery reads cannot replace a client holding unresolved requests. Page suspension/restoration also reconnects that same client, preserving pending commands while requiring fresh server-confirmed subscriptions. No retry is sent automatically. Existing unmarked recovery behavior remains unchanged.

These intentions live in the current client instance, not durable browser storage. Full reload, leaving the room, epoch change or account change must not be presented as preserving its retry queue. The UI tells the referee to keep this page and confirm rather than re-add points. Durable intent recovery across a full reload remains future work and is not certified here.

The native Emulator browser suite deliberately discards a successful score reply, observes the committed score, reconnects with the actual formal recovery control, and uses the actual retry button. For both 6/12 courts it requires identical original/retry payloads, exactly one accepted score increment, unchanged private root and no remaining retry button after confirmation. The surrounding page/renderer is still an isolated harness, and App Check remains an Emulator-only fixture.

## Reviewed operator migration candidate

`bucket-migration-plan.cjs` and `bucket-migration-service.cjs` add an internal operator factory with read-only preflight and atomic commit. They are not exported by the formal Functions index and do not enable a production room. The separately gated operator CLI below wraps this internal factory without adding a public endpoint. The caller must supply an already verified operator identity; reading an active non-test super_admin profile is an additional check, not an external identity verifier. The CLI provides a verified identity boundary; production IAM/identity acceptance and the remaining rollout checks are still required.

Preflight reads a consistent root, complete bucket query, public mirror and configuration, then returns only identifiers/counts, source versions, conservative size estimates and a SHA-256 digest. It writes no marker, receipt or backup. Commit rereads all sources in the same lock order as scoring/projection and requires that exact digest; a score, room/public/config change invalidates the plan. Activation rejects every existing bucket, including IDs beyond the expected bucket count, and rejects non-official, partner, team, nonstandard, non-single-elimination, closed and malformed rooms. The local transaction policy allows at most 100 buckets, 750,000 serialized bytes per checked document and 5,000,000 aggregate checked bytes; these are conservative application budgets, not claims about unlimited Firestore capacity.

Each accepted operation atomically creates three protected backups: full private root, full public document, and materialized state plus manifest. A receipt records hashes, operator, logical room ID, generation, time and result. A unique per-room generation ledger remains after rollback, preventing epoch reuse. Same-identity/same-operation replays return the original result without rewriting data; conflicting operation reuse and revoked operators are rejected. Backup hashes verify Firestore serialization round trips, including timestamp fields; they detect corruption, not a malicious IAM principal able to rewrite both backups and receipts.

Rollback verifies the activation receipt/backups, reads every current bucket and materializes the latest scores/logs. It backs up this current state, restores the canonical root/public view, removes the marker/projection metadata and deletes all buckets in one transaction. It never restores the activation-time stale score JSON. A stale rollback plan fails instead of discarding a concurrent accepted score. Missing/mixed buckets or invalid backups stop rollback; this is not an automatic disaster restore from incomplete data.

Production construction requires a separate `BXH_BUCKET_MIGRATION_ENABLED=true` gate, explicit matching non-demo project and no Emulator/debug environment. Activation additionally requires all existing production score gates, private read/automatic projection flags, migrationEnabled and an exact migrationRooms[code] epoch. Rollback deliberately does not require the scoring runtime, enabled or migrationEnabled flags, so a stopped scorer does not trap an already partitioned room; it still requires the migration runtime, current super_admin profile, exact epoch and verified activation backups. No flags or allowlist entries are changed by this commit.

Candidate Rules explicitly deny every client get/list/write of bucketMigrationBackups, bucketMigrationOperations and bucketMigrationEpochs, including a browser signed in as super_admin. The root migration metadata is server-owned. These remain undeployed candidate Rules and must be reconciled against live Rules before release.

The dedicated Emulator suite covers reviewed 6/12-court cutover, concurrent score writes, stale-plan refusal, rollback after scorer/config shutdown, newest score/ledger preservation, receipt replay, revoked operators, generation reuse, a score/rollback race, corrupted backups and an out-of-range orphan. It uses only the exact demo project/loopback host. This prepares a reviewable migration boundary; it does not certify the full production page, all trusted writers or an operational rollout.

## Verified migration operator CLI

`scripts/bucket-migration-operator.cjs` provides three explicit commands: preflight, inspect and commit. It adds no HTTP endpoint or browser management API. The script requires Node 22+ and access to the pinned Admin SDK dependencies; the repository functions directory dependencies can be supplied through NODE_PATH. No command changes environment gates, project settings or room allowlists.

Both network commands require an explicit project/runtime and a local ID-token file. Before reading credentials or initializing Firebase, the script checks project/environment agreement, the closed migration runtime gate and exact Emulator hosts for a lab run. Production additionally uses Application Default Credentials and the existing project IAM permissions. An emulator/debug environment cannot be used with production runtime. These gates do not make this candidate production-ready.

`bucket-migration-operator.cjs` in the Functions source verifies the ID token with checkRevoked=true, verifies its project issuer/audience/UID, then derives actorUid from the verified result. It does not accept a caller's actorUid. The migration service independently rechecks the current non-test, active super_admin profile inside each transaction, including receipt replay. Production token validation and IAM access still need real-environment acceptance; Emulator tests cannot certify production cryptographic verification or IAM policy.

Preflight creates a new private review file with the source plan, verified actor, project, one operation ID and a review checksum. Existing files are never overwritten. Inspect is offline/read-only and prints only room/action/epoch/counts/project/checksum. Commit requires the review file and the separately supplied expected review checksum; it verifies the current token again and requires the same actor/project. Repeating commit with the same file reuses the operation ID, including when the first result was lost. The review checksum detects a file changed since review; it is not a secret, signature or authorization grant. Server-side source revalidation remains authoritative.

Token/review input must be a regular, privately readable file owned by the current OS user; symlinks, group/world permissions and oversized input are rejected in the tested Linux environment. Tokens never appear in command arguments, review output, stdout or error details. Use a trusted sign-in flow to obtain the token directly into an appropriate local file; do not paste it into chat or logs. The CLI uses a bounded deadline; a timed-out commit reports outcome unknown and must be resolved by retrying the same review, not by inventing a new operation.

Command shapes (no production enablement flags are provided here):

```text
node scripts/bucket-migration-operator.cjs preflight --runtime MODE --project PROJECT --token-file LOCAL_FILE --action activate|rollback --code ROOM_CODE --epoch UNIQUE_EPOCH --out NEW_REVIEW_FILE
node scripts/bucket-migration-operator.cjs inspect --plan REVIEW_FILE
node scripts/bucket-migration-operator.cjs commit --runtime MODE --project PROJECT --token-file LOCAL_FILE --plan REVIEW_FILE --expect-digest REVIEW_CHECKSUM
```

The dedicated Auth/Firestore Emulator suite invokes real child CLI processes for 6/12-court preflight, inspection, activation/replay and rollback/replay after scoring is disabled. It uses real Email/password Emulator ID tokens, rejects a disabled Auth user, player profile, manually supplied UID, another operator and changed review, verifies no preflight writes or duplicate migration, preserves the latest accepted score, and checks that credential files never enter reports.
