## 追加優化：持久化輕量卡位（2026-11-26）

新的候選 `hold-service.cjs` 將卡位寫入房間子集合 `registrationV3Holds/{uid}`，只含 UID、序號、時間、狀態、去重識別。房間子集合已包含房號，避免重複保存。每房一份 ledger 保存容量及修訂號；不讀整張報名表。審核通過才寫 A 卷 registrations；B 卷摘要由後續分批同步處理（尚未介接）。舊 service.cjs 僅保留為先前交易及名單投影測試基準，不能與新服務同時啟用。

卡位交易預期固定 5 次文件讀、3 次文件寫（不含權限額外讀取、索引及重試）。審核通過多讀參賽者與正式列、多寫正式列。這些為程式路徑計數，不是正式帳單量測。ledger 仍是單房競爭點，須由真實並行測試判定是否需要分配固定容量的分桶；不得用不受限分散計數取代硬容量限制。

驗收：192 人同時報名、最後名額競爭、重送、程序重啟、審核及釋位、B 卷同步延遲及故障恢復；紀錄每次交易讀寫、重試、延遲分位數及審核完成時間，與同條件 V1/V2 比較。區分 API 批次與計費文件寫入；320 人後續挑戰，未實測不宣稱通過。既有 Firestore 優先；不新增付費服務。正式 callable、Rules、摘要同步及發布仍待完成。

## Firestore 模擬器首次實測

本機 Firestore 1.19.8，192 名額／193 個合成帳號。直接並行結果僅 2 筆成功、191 筆 ABORTED；串行對照 192 筆成功、1 筆 full。兩者均沒有超額或已提交卡位遺失。單 ledger 並行性能未通過，不能發布。詳見 `evidence/emulator-wave-20261126.json`。讀寫為交易程式計數，不等同正式計費；下一步比較降低競爭的持久化容量分配方案並重跑同一驗收。
