# 主房分組賽候選

新版操作在主房按一次「一次抽好各組」，先建立 A～D 的分組名單及四間子房對戰表，僅開放 A 組入場。各組仍依順序開賽與回收，A 組回收後直接開放已抽好的 B 組；名次賽仍需等四組結果收齊後再抽。已在進行中的舊分組房維持原本流程。分組與子房的建立分別使用兩筆可重試交易；第二筆失敗時管理頁提供「完成各組對戰表抽籤」沿用原分組名單重試。

主辦在人員管理的對戰表先選 2 組或 4 組，再按「分組抽籤」。系統按有效名單平均分配，餘數依組別順序各加一人，抽定後鎖定組數。組數與每組容量分開設定，目前每組至多 96 人，因此 2 組合計最多 192 人、4 組最多 384 人。128 人選 2 組時為 64／64，320 人選 4 組時為 80／80／80／80。未來 512 人分成 4 組各 128 人，須先驗證分組寫入、對戰、分流及結算，再調高容量。

`firebase-entry.cjs` 提供 Callable 候選，操作者從驗證後的 request 取得。管理操作要求管理員角色，所有玩家入口限定在伺服器啟用的主房。分組與收件保存在伺服器私有的 `groupStagePlans`。玩家只讀取簡短進度和自己的分組資料，當前有出賽資格才會收到房號。分組房沿用一般單淘汰的房間資料格式，正式積分由主房結算。

`coordinator.readSettlement(tx, parentCode)` 在同一交易中檢查主房、報名身分和各階段的完成狀態，供現有天梯入帳流程接入。未晉級選手依淘汰輪次並列名次。四組賽取前八名，兩組賽由兩組冠軍打第 1～2 名、兩組亞軍打第 3～4 名。未晉級的準決賽敗者分別並列第 9 名或第 5 名。積分權重沿用有效出賽人數。

管理員可用 `settlement-preview` 取得完成後的有效人數、名次分布及預計積分總量；此入口在唯讀交易中重查主房與報名，演練房不可用，也不會寫入任何天梯紀錄。它只供核對，不能代表積分已入帳。正式入帳仍需接上當前部署的天梯服務，確認大型賽容量、防重複入帳及賽季保護後再發布。

本候選可在隔離 Firestore 中建立子房、讀取分流入口與收回賽果。正式發行前需接上管理與玩家介面、驗證發行包和正式 Firestore 規則，以及把主房結果接到現有天梯交易。測試使用合成帳號，積分紀錄寫入為零。

不公開一般房可用於管理員演練。房號需同時列入 `systemConfig/groupStages.parentCodes` 與 `rehearsalParentCodes`，管理員進入不公開一般房的賽事編排時，前端透過具 App Check 的分組入口查詢後端允許狀態。演練房關閉線上報名，名單限未綁定帳號且不計積分的現場訪客，子房保持不公開。賽果可回收，結算入口會拒絕演練房。分桶子房由伺服器在同一交易回讀計分分桶，資料缺漏時保留當前階段供重試。

### 單房演練發布

1. 從已驗證的提交執行 `node group-stages/prepare-release.cjs /tmp/bxh-group-stages-release`。輸出為獨立 Firebase Functions codebase，僅匯出 `groupStageCommand`，不包含 Hosting 或 Firestore 規則。
2. 確認正式的 `systemConfig/groupStages` 尚未開啟本次演練房號。發布後端時將範圍限定為 `functions:arena-group-stages`，驗證函式位於 `asia-east1` 且拒絕未登入的請求。
3. 前端發布後，先核對正式站 `release.json` 對應已驗證的提交，再由有權限的操作者將指定不公開一般房加入後端的 `parentCodes` 與 `rehearsalParentCodes`。保留其他現有設定。
4. 以管理員開啟指定房的賽事編排，確認可選 4 組。另選一間未允許的一般房，確認只顯示原本的抽籤流程。若需停止演練，從兩份名單移除指定房號。
