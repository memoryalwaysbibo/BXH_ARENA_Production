# General bucket completion and certified hosting candidate

Not deployed. No feature flags, runtime settings, room activation or production data have been changed. The new `completeBucketTournament` entrypoint defaults to production mode and requires the existing runtime/project/room-epoch gates plus a new `systemConfig/fourCourtScoreBuckets.completionEnabled === true`. No helper enables those gates.

Supported scope: official, individual, standard, single-elimination **general** rooms using the existing referee-seat/bucket protocol, 1–32 physical courts, with or without the bronze match. General completion never resolves participant account identities, reads ladder season state, credits points, creates ladder transactions or changes existing award flags. Community/test/partner, double-elimination, round-robin, team and enchantment completion are outside this candidate. Existing bucket scoring already requires official rooms.

The caller supplies only code, physical room ID and unique manifest epoch. Within one transaction the handler rechecks the actor's current active admin role or staff ownership, both roots, runtime/allowlist, every active bucket, root/bucket SDK createTime, revision vector and complete SE topology. It derives final placements from those matches and writes canonical private/public completion plus paired QR advancement. Both roots commit together; buckets are unchanged. A private certificate binds parent creation time, epoch, full revision vector and canonical state SHA-256. The public receipt excludes actor UID and source identity. Replay rechecks authority/gates/state and performs zero writes. Migration/deletion fields are fences by presence, including null/false. Old unverified completion/award markers, changed generations, corrupt/missing buckets and oversized documents stop without clearing anything.

Hosting patches are pinned independently to the captured sources for `preserveCompletedRoomAndCountHost` (set15) and `preserveExistingCompletedRooms` (set16). The room trigger rejects an older physical generation's event. Certified general or PR713 ranked completions are read and verified within the ledger transaction; first ledger creation, host counter increment and title outbox commit together. A code-reused/unmarked historical ledger is never adopted automatically. No bucket root JSON is rewritten by hosting.

The daily rebuild now discovers host IDs in pages and recomputes **each host** from a fresh transactional room query and profile, current roots/peers/buckets/certificates, old ledgers and host stats. The earlier global scan's count is not used for absolute counter writes. Concurrent room completion/ledger creation/stat increments conflict and retry, so a delayed scan cannot overwrite a newer increment. Invalid marked rooms stop that host's rebuild before writes, preserving its previous count; other already-committed hosts need no rollback. Per-host limits are 200 rooms and 5MB of input; exceeding either also leaves that host unchanged. A legitimate active, uncompleted bucket room contributes zero rather than an unverified completion. Title outbox writes commit with the rebuilt count.

`syncMyHostingProgress` appears in the same copied source, but its **own deployed archive is still missing**. Its copied export is adapted for consistency only; it is not a deployment target and no source equivalence is assumed. Capture/review and upgrade that independent function before enabling buckets, or it could still reset counts using legacy state. Do not deploy any sibling functions from these old captured source sets. When assembling a hosting source archive, replace its root `hosting.js` with the respective candidate and add `certificate.cjs`, `hosting-guard.cjs` and the pinned `protocol/` under a new root `bucket-completion/` directory. The candidate root import is `./bucket-completion/hosting-guard.cjs`; this repository review layout is not itself a ready-to-deploy hosting archive.

Validation includes local synthetic transactions, the actual captured hosting trigger with fixture SDK boundaries, and a real Firestore SDK Emulator workflow. They are not real Auth/App Check, Eventarc delivery or browser acceptance. The new general endpoint is not yet connected to PR714's ranked-only frontend receipt path. The next integration must bind the ranked callable request to the browser's expected room ID/epoch as well as connect general completion, then exercise both paths end-to-end. Broader writer inventory, derived consumers and six-court cutover/rollback acceptance remain required.
